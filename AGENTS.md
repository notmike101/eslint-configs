# AGENTS.md

## Purpose

This is a private workspace of general-purpose flat ESLint configuration packages under `@notmike101`, not an application repo. The root and every config package must remain private and must never be published. Local tarballs and workspace dependencies are the supported consumption paths.

## Workspace Shape

- Package manager: `pnpm`
- Required runtime: Node `>= 22`
- Expected pnpm version: `>= 10`
- Private config packages live under `packages/`
- Shared JS and TS authoring source lives under `internal/config-fragments/`
- Repository tooling lives under `scripts/`
- Consumer-shaped validation fixtures live under `fixtures/`
- Fixture and integration tests live under `tests/`
- Active packages in this workspace:
  - `packages/eslint-config-js`
  - `packages/eslint-config-jsdoc`
  - `packages/eslint-config-ts`
- `packages/eslint-config-tsdoc/` is not an active package. Do not build it out unless the user explicitly asks.

## Default Working Model

Most changes in this repository should be package-scoped, but JS and TS are no longer hand-authored entrypoints.

When changing rules or behavior:

- For JS and TS shared behavior, edit the internal fragment source under `internal/config-fragments/`
- Regenerate `packages/eslint-config-js/index.js` and `packages/eslint-config-ts/index.js` with `pnpm run generate`
- For JSDoc, edit the package entrypoints directly
- Keep the change isolated to the affected package unless the rule truly needs to stay aligned across multiple packages

Keep rule behavior unchanged unless the task explicitly requests a change. Mirror shared JS and TS behavior in the fragment source rather than editing generated entrypoints independently.

## Editing Rules

- Preserve ESM exports and the current package entrypoint structure
- Keep rule-source comments and documentation links near rules you add or change
- Avoid broad formatting sweeps unless the task is explicitly a formatting cleanup
- Do not rewrite unrelated sections of large config files just because they could be normalized
- Do not hand-edit generated JS or TS entrypoints unless the user explicitly asks for a generated-file fix
- Do not bump the root `package.json` version for ordinary package changes
- Do not touch `pnpm-lock.yaml` unless dependencies actually changed
- Keep the `@notmike101` namespace and `private: true` in all package manifests; do not add publishing or release automation

Be careful with JS and TS config files:

- `packages/eslint-config-js/index.js` and `packages/eslint-config-ts/index.js` are generated by `scripts/generate-configs.mjs`
- The source of truth for shared JS and TS rules is `internal/config-fragments/`
- `packages/eslint-config-ts/index.js` still uses TypeScript project-service parsing behavior when linted directly

That means consumer-shaped fixture validation is more representative than trying to self-lint generated config files directly.

## Validation

Preferred validation entrypoints:

- `pnpm run generate:check`
- `pnpm run validate:imports`
- `pnpm run test:fixtures`
- `pnpm run pack:check`
- `pnpm run ci`

`pnpm run ci` is the repo-wide compatibility workflow and should be the default validation target for broad changes.
Run validation locally; do not assume Git metadata, remote branches, or GitHub Actions are available in this exported tree.

The import smoke test still exists as a fast targeted check:

```powershell
pnpm run validate:imports
```

Fixture and packaging validation are now first-class:

- `pnpm run test:fixtures` validates the packages the same way downstream consumers import them
- `pnpm run pack:check` verifies packed tarballs in temporary consumer installs, not just workspace links

Optional package-local checks:

- From `packages/eslint-config-jsdoc`:
  - `.\node_modules\.bin\eslint.cmd --config index.js index.js`

Known caveats:

- Generated JS and TS entrypoints are implementation artifacts, so fixture validation matters more than self-linting them directly
- `eslint-config-ts` still relies on project-service parsing behavior for its consumer-shaped TS tests

Do not treat those caveats as a reason to skip the repo-wide compatibility workflow.

## Good Agent Behavior Here

- Read the affected config, its authoring source, and consumer fixtures before changing behavior
- Keep guidance self-contained; do not link to absent documentation, workflows, or repo-local skills
- Keep changes tightly scoped to the requested config package or shared fragment source
- Call out when a change probably should be mirrored between JS and TS configs rather than guessing
- Regenerate JS and TS entrypoints after changing shared fragments
- Prefer fixture and pack validation over self-linting generated config files
- Report the validation commands actually run and their results; state explicitly when checks were not run
- Leave ordinary config changes unversioned; there is no changeset or registry-release workflow
